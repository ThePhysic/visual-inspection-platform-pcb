## Measurement environment and interpretation

10.0.26200, approximately 32 GiB RAM. Docker Desktop Linux engine 29.9.1 on
WSL2 kernel `6.18.54.1-microsoft-standard-WSL2`, 16 logical CPUs and approximately
15.2 GiB available to the engine. Native Node 24.22.1, pnpm 10.34.7; application
containers pin Node 24.22.0. DL uses Python 3.12.15, Torch 2.7.1+cpu,
TorchVision 0.22.1+cpu and four Torch CPU threads. No GPU is requested or used.

The real runner records actual container/resource observations and revisions in
`acceptance.json`. It separates image/upload acceptance, durable inspection
creation, queue wait, HTTP inference/JSON decoding, Python stages, result commit,
API-observed completion (100 ms polling), and browser visibility (2 s polling).
First prediction after readiness excludes process/bundle startup; whole-stack
creation-through-health is a separate observation, not pure model-loading time.

Thirty sequential API workflows cycle four attributed 300×300 patches. Twenty
sequential browser workflows repeat the training-set serving fixture. These are
different workload definitions. Nearest-rank p50/p95 describe the recorded samples;
there is no p99, calibrated accuracy, production-capacity or SLA claim. Resource
samples are point observations, not peak measurements. The existing unrelated
PostgreSQL container remains running on the host.

The original 113 ms mock visibility benchmark and the DL warmed Python-only
54 ms CPU / 37 ms GPU measurements do not represent this integrated workload.

Upload timing includes the harness reading the small local fixture and decoding
the response. Created-to-claim includes insertion, rather than measuring pure
Redis residence or starting exactly at HTTP acknowledgement. Worker processing
ends before conditional commit; commit is a separate measurement. Python timing
excludes ASGI serialization and networking. Browser timing includes Playwright
observation overhead, and excludes file selection and readiness checks. Percentile
columns are separate distributions and must not be added together.

The first prediction after readiness took **109.72 ms HTTP** (**n=1**). Fresh
six-container creation through healthy status took **20.08 seconds** with cached
images. These boundaries exclude image building, and neither is a distribution of
pure model loading time. Warm HTTP max was **117.00 ms** in this run. Based on these
observations, the existing **8 s HTTP / 10 s attempt / 30 s lease** and 45 s worker
shutdown grace were retained; slower devices or unusually slow requests can still
exhaust the finite budget. These measurements establish no SLA.

The API batch completed **6.02 inspection workflows/second**, concurrency one,
with **0/30 failed workflows** and **0 busy application attempts**. The JSON field
`requestsPerSecond` counts completed inspection workflows, not individual HTTP
requests. The separate three-concurrent-request capacity probe returned **1/3
success and 2/3 busy**; it is not a throughput benchmark. Container CPU and memory
snapshots are preserved in `resourceSamples`; no peak-resource claim is made.
The three model-container samples observed **311.9–316.1 MiB** memory usage;
the midpoint sample showed **146.34% Docker CPU** (about 1.46 logical CPUs),
while the two idle-boundary samples showed 0.20% and 0.42%. These are three observations,
not resource distributions or maximum usage.

Separate live fault probes now demonstrate application-level behavior: a genuine
incomplete JPEG upload holds Python admission, yielding typed `inference_busy`
through the real worker adapter. A queued busy failure was observed on attempt
two and trained completion on attempt three, without fallback. Pausing the owned
Python container produced a durable `PROVIDER_TIMEOUT` on attempt one, then
trained completion on attempt two after unpause. Restoration through fresh
health and observed completion took 6.54 seconds in this single fault probe;
it is not a latency percentile or an SLA.

The model-outage inspection was accepted while the API remained ready, failed
after exactly **three** real attempts with no predictions, and completed through
an identity-preserving linked manual retry after recovery. During a separate Redis
outage, submissions and repeated keys retained one durable intent. The in-flight
SIGKILL scenario recovered on **attempt two** after lease expiry. Python's internal
completion of the disconnected first request was not individually observed;
late-commit fencing additionally has deterministic execution/integration tests.
Down/up preserved the trained original result, provider identity and saved review
at **revision two**.

## Evidence and limitations

The real runner generated actual Python responses, browser captures, timing
samples, outage/retry and restart evidence. The training-set response in
[python-response.json](python-response.json) is checked by a mandatory backend
regression test; no missing-artifact skip or simulated substitution is used.
The four `trained-*.png` files are direct Playwright screenshots, without image
retouching or compositing. [Browser measurements](browser-warmed.json) and the
[initial workflow observation](browser-workflow.json) record their exact scopes.
Review edits in the demonstration illustrate UI operations and are not expert
adjudication of PCB ground truth. The sample attribution and audited split
provenance are in [fixtures/pcb](../../fixtures/pcb/README.md).

Input admission combines canonical 300×300 geometry with explicit human domain
attestation. It does not automatically recognize whether pixels depict a PCB.
No whole-board search, tiling, online learning or retraining is included.
The model's 44.17% AP50 and 27.19% AP50:95 apply to the DL frozen 722-image
holdout study, not this application. Scores are uncalibrated; false alarms,
missed defects and weak rare-class support remain. The project is unaffiliated
with Matroid and is not validated for production manufacturing inspection.

Publication preflight scanned both Git histories with redaction and read-only
mounts. The platform scan found no candidates; all ten DL generic-key candidates
were public Python source SHA-256 values, each verified against actual historical
Git source bytes. [Classification evidence](publication-scan.json) records the
raw counts and zero unresolved candidates. Tracked configuration inspection found
only `.env.example`; no credentials, private keys or unrelated workspace files
were selected for delivery. This is a publication check, not a comprehensive
security certification.

The finish-project delivery uses independent Astra medium adversarial review.
The delivery tag identifies the reviewed commit; private remote visibility and
matching local/remote commits are verified as the final publication step.
